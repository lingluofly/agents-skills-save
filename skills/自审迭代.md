## 适用范围

- 适用：任何自定义 skill 至少被完整使用过一次、拿到了真实产出物之后，审查产出质量并决定是否修改 skill。
- 不适用：第一次撰写 skill（还没有使用样本）；单纯让执行者重做一次产出。

## 核心原则：先归因，再动手

产出不达标时，原因只有两类，处理方式完全不同，不许混淆：

1. **执行偏差**：skill 里已有明确规则，执行者（人或 AI）没有遵守。
   → **不改 skill**。把具体偏差点反馈给执行者，要求重做或下次调用时强化指令。
   → 同一规则**连续 2 次真实使用都被违反**，才升级处理：把规则提到更靠前的位置、配反例、或加进交付前硬门禁。
2. **规则缺陷**：产出踩的坑在 skill 里找不到规则、规则互相矛盾、或规则不适用于实际场景类型。
   → **才改 skill**，按下面的流程改。

拿不准归哪类时，默认归为执行偏差。防止 skill 越补越肿。

## 闭环四步

### 1. 使用（留样本，但不入库）

- 每次使用 skill，留存三样东西：原始素材、调用指令、产出物。
- 注明 skill 名称与使用日期。没有样本就没有迭代依据。
- **样本不许放进 skills 目录或任何 git 跟踪的仓库目录**，避免随仓库提交。样本留在仓库外的原位（下载目录、临时文件夹均可），审查用完即可，不承担长期引用职责。
- 长期保留的是**教训而不是样本原文**：审查结论、归因、典型反例（脱敏后一两句话）记入项目 memory。日后迭代查 memory，不依赖样本文件还在不在。

### 2. 反馈（双关审查，缺一不可）

- **第一关 · 对清单**：用 skill 自己的"交付前自检清单"逐条核对产出物，记录命中/未命中。
- **第二关 · 对素材**：把产出物与原始素材逐项对 diff，重点查：
  - 数字、枚举数量（素材点名 4 个，产出不能写 5 个）、专有名词、名称；
  - 时间承诺、补偿承诺、未官宣信息；
  - 产出中出现但素材里不存在的"事实"和推断。
- 出具审查结论：问题逐条列出，每条标注 `[执行偏差]` 或 `[规则缺陷]`，并引用 skill 中对应的条目（没有对应条目的，即规则缺陷）。

### 3. 修改（只改规则缺陷，最小改动）

- 每条缺陷对应一处最小修改：补规则、补正反例、收紧口径、或为新场景增加类型分支。
- **不针对单次样本写特判条款**，新规则必须能覆盖一类情况。
- 优先增加"动作/检查点"（如"交稿前对一次 diff"），少加形容词式叮嘱（"要严谨""请注意"）。
- 新增规则时检查是否有可合并、可删除的旧规则，控制篇幅。
- 在被改 skill 末尾维护"变更记录"：日期、改了什么、为什么，**一条不超过两行且必须自包含**——读者只看这条就能知道改了什么，不写样本路径/链接，也不写"细节见 memory/笔记"式的指向（外部读者访问不到本机文件，任何指向都是死链）。
- **硬门禁：教训没记入项目 memory，不允许写变更记录条目。** memory 是完整教训的存档处（供本机日后迭代回看），skill 里的变更记录则必须自包含；两者各写各的，不在 skill 里互相指引。

### 提交卫生：入库文档不许出现被忽略文件的记录

skill 等入库文档会随 git 提交，别人 clone 后看到的只有被跟踪的文件。因此：

- 动笔引用任何文件路径前，先查仓库 `.gitignore`。凡是被忽略的文件或目录（当前包括 `memory/`、`ai-workbench/` 等），**在入库文档中一律不出现**：不写相对路径、绝对路径、`file://` 链接、文件名。
- 教训、样本、内部配置这类只存本机的内容，细节只写进本机 memory；**入库文档不指向它们，连"细节见本机项目 memory"这种话都不写**——外部读者访问不到，任何指引都是死链，需要交代的前因后果直接写进条目本身。唯一例外：规则正文本身就在讲"教训存哪里"这一机制时，才允许出现 memory 这个词。
- 入库文档中允许出现的文件引用，只限于已被 git 跟踪的文件。提交前用 `git status` 自查，或用 `git check-ignore <路径>` 确认引用目标未被忽略。
- `.gitignore` 新增忽略规则时，回头检查已入库文档是否已有该路径的残留引用，有就删掉。

### 4. 再使用（回归验证）

- 下一次真实使用该 skill 时，带着上次的变更点做针对性验证：新规则是否被遵守？同类问题是否消失？
- 验证通过，闭环关闭；仍被违反，按"连续违反升级"处理（前置、加反例、硬化为门禁），不重复堆砌同义规则。
- 只改不验 = 迭代未完成。

## 产出审查报告的推荐格式

```
样本：<skill 名> 第 N 次使用（日期）
一、未命中清单
1. <问题描述> [执行偏差/规则缺陷] → skill <条目名>：<引用或"无此规则">
二、归因结论
- 执行偏差 X 条（反馈执行者，不改 skill）
- 规则缺陷 Y 条（进入修改）
三、skill 修改方案（仅规则缺陷）
- <条目>：<改什么，覆盖哪一类情况>
四、下次回归验证点
- <新规则在下次使用时怎么验>
```

## 常见误区

- **把执行偏差当规则缺陷**：skill 已写"数字要有出处"，产出仍编数字。正确反应是增加一道可执行的检查动作（对 diff、逐个点名），而不是把同一句话换措辞重写三遍。
- **只凭感觉审查**：只看产出"顺不顺"，不对清单、不对素材。事实性错误（编造数字、新增承诺）只有对 diff 才能发现。
- **只改不验**：修改后没有下一次真实使用的回归，迭代不算闭环。
- **膨胀式迭代**：每次都往 skill 里加段落。先做归因，执行偏差一律不进 skill。
- **把样本塞进仓库**：样本文件复制进 skills 目录会被 git 跟踪提交，膨胀仓库且路径搬迁后引用全部失效。样本留仓库外，教训进 memory。
- **文档里引用被 gitignore 的文件**：文件不提交、路径却写在提交的文档里，别人 clone 后引用全是死链。被忽略 = 在入库文档中彻底消失，连路径和文件名都不留。
