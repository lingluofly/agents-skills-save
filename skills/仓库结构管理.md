## 适用范围

- 适用：新项目目录骨架设计、老仓库结构整理/重构、判断"新文件该放哪"、审查目录合理性。
- 不适用：代码内部重构（函数/模块级）、依赖管理、构建配置调优。

## 动笔前必须确认的信息

1. **项目类型与技术栈**：框架自有约定（如 Next.js 的 `app/`、Vue 的 `src/components/`、Java 的 `src/main/`）**永远优先于**本 skill 的通用规则。
2. **现有结构**：整理老仓库时必须先读现有目录树，在现状基础上改进。不许不看现状直接画一棵"理想树"。
3. **团队既定约定**：已有 CONTRIBUTING、架构文档或明显的主流命名风格时，跟随现状，不强行统一成本 skill 的偏好。
4. **操作权限**：本任务是"只出方案"还是"直接动手"？涉及移动/删除时，默认先出方案等确认。

## 结构原则

### 分层

1. **扁平优先**：目录嵌套 ≤ 3 层。觉得需要第 4 层时，先问自己：是目录太深，还是这个模块该独立出去了？
2. **聚合方式二选一，全仓库统一**：
   - 按类型分（`components/`、`utils/`、`hooks/`）——适合小项目；
   - 按领域分（`order/`、`user/`、`payment/`，每个领域内部自含组件与逻辑）——适合中大型项目。
   - 禁止一半按类型、一半按领域混用。
3. **YAGNI**：不为"将来可能用到"提前建目录。目录因第一个真实文件而存在。

### 文件归位

4. **先找归宿再新建**：新增文件前，先检查已有目录能否收容它。能放就不建新目录。
5. **一个目录一个职责**：能用一句话说清"这个目录装什么"。说不清的就是拆分或合并信号。
6. **警惕垃圾桶目录**：`utils/`、`common/`、`helpers/`、`misc/` 全仓库最多各一个，且每个文件放进去前必须回答"为什么它不属于某个具体领域"。
7. **根目录洁癖**：根目录只放必备项（README、LICENSE、配置、入口级目录）。文档归 `docs/`，脚本归 `scripts/`，示例归 `examples/`。

### 命名

8. 目录名：小写，单词分隔符全仓库统一（kebab-case 或 snake_case，跟随现状）；单复数统一（有 `docs` 就别再出现 `asset`）。
9. 名字表意不表形：用 `order/` 不用 `module1/`、`new/`、`temp/`、`backup/`。
10. 不使用含义重叠的并列目录：`lib/` 和 `libraries/`、`src` 和 `source` 只能留一个。

## 红线（违反 = 打回）

1. **破坏性操作先列清单**：任何移动/删除/重命名，先输出完整变更清单（源路径 → 目标路径）等用户确认，再执行。不边想边动。
2. **移动必更新引用**：文件移位后，必须同步检查并更新：import/require 路径、配置文件、构建脚本、文档与 README 中的链接。给出检查清单，不假设"应该没人引用"。
3. **禁区不动**：`.git/`、`node_modules/`、构建产物（`dist/`、`build/`）、IDE 配置目录，一律不整理、不移动、不删除。
4. **不建空目录**：不允许用 `.gitkeep` 占位一个没有任何真实文件的目录（框架强制要求的除外）。
5. **敏感文件检查**：整理过程中发现密钥、`.env`、证书等已被提交，立即提醒加入 `.gitignore` 并说明历史清除方法，不默默略过。
6. **不滥建文档**：目录结构调整不附带新建 README/说明文档，除非用户明确要求（单个复杂目录可在现有文档中补一句职责说明）。

## 常见 AI 痕迹（必须避免）

- 给小项目套大项目架构：3 个文件的脚本项目也分出 `src/main/handler/`。
- 每个目录都配一个 README.md。
- 画一棵完美对称的树：所有领域目录内部结构强行一致，实际内容根本不对称。
- 输出"建议结构"但不给从现状到目标的迁移步骤。
- 创立只有 1 个文件的目录且说不出第二个文件会是什么。

## 输出格式

### 出方案时

```text
1. 现状诊断：当前结构的问题清单（每条注明依据）
2. 目标结构：树状图 + 每个目录一句职责说明
3. 迁移步骤：按顺序列出 新增/移动/删除 操作（移动标注引用更新点）
4. 风险点：可能影响到的构建、引用、第三方配置
```

### 只回答"文件放哪"时

直接给路径 + 一句话理由 + 是否建议新建目录。不长篇分析。

## 示例

**场景**：用户问"我新写了一个导出订单报表的脚本，放哪？"

**差的回答**：
> 建议在根目录创建 `scripts/export/reports/` 目录，并新建 `README.md` 说明用途……

**好的回答**：
> 放 `scripts/export-order-report.py`。`scripts/` 已存在，直接放；这是第一个导出类脚本，等出现第二个再考虑建 `scripts/export/` 子目录。

## 交付前自检清单

- [ ] 框架约定和仓库现状优先于通用规则？
- [ ] 嵌套 ≤ 3 层？聚合方式（类型/领域）全仓库统一？
- [ ] 每个新目录都有真实的第一个文件，且说得出第二个文件可能是什么？
- [ ] 根目录无散落文件？无空目录、无垃圾桶目录滥用？
- [ ] 目录命名风格（大小写、分隔符、单复数）与现状统一？
- [ ] 所有移动/删除操作已列清单并经用户确认？
- [ ] 每个移动操作都标注了引用更新检查点？
- [ ] 禁区目录零触碰？无新建的多余文档？
