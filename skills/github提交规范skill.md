## 适用范围

- 适用：撰写 commit message、批量整理提交记录（rebase/squash 时改写）、生成 PR 标题。
- 不适用：代码审查、CHANGELOG 撰写、分支命名、发布说明（release notes）——这些可复用本规范的部分规则，但不完全等同。

## 动笔前必须确认的信息

1. **仓库现有风格优先**：先看最近 20 条 `git log`。仓库已有固定格式（含语言、是否用 scope、是否用 gitmoji）时，一律跟随仓库，本 skill 只补空缺。存在 commitlint 配置 / `.gitmessage` / CONTRIBUTING 中的提交规范时，以仓库规范为准。
2. **语言**：中文还是英文？未指定时跟随仓库历史的主流语言。一条 message 内中英不混用，同一分支的 message 语言保持一致。
3. **实际改动**：必须基于真实 diff 或用户提供的改动清单。只有文件名、没有改动内容时，追问，不许凭文件名猜意图。
4. **背景信息**：是否 breaking change？是否关联 issue/需求单号？用户没说就主动问一次。

## 格式规范

```text
type(scope): subject

body（可选）

footer（可选）
```

### type 白名单（只允许这些）

| type | 含义 | 何时用 |
| ---- | ---- | ------ |
| feat | 新功能 | 用户可感知的新能力 |
| fix | 修复缺陷 | 线上/测试确认的 bug |
| docs | 文档 | 只改文档，不改代码行为 |
| style | 格式 | 空格、分号、格式化，不改逻辑 |
| refactor | 重构 | 不改外部行为的代码调整 |
| perf | 性能 | 以提升性能为目的的改动 |
| test | 测试 | 新增/修改测试 |
| build | 构建 | 依赖、打包、构建脚本 |
| ci | 持续集成 | CI 配置与脚本 |
| chore | 杂务 | 不属于以上任何的杂项 |
| revert | 回滚 | 回滚之前的提交 |

拿不准 type 时，按"这次改动的主要意图"归类，不许为省事一律用 chore。

### subject（必填）

- 长度 ≤ 50 字符；中文 ≤ 25 字。
- 动词开头、祈使句。英文用 `add/fix/remove` 原形，不用过去式/进行时；中文用"新增/修复/移除/重构"，**不用"了"**。
- 结尾不加句号等任何标点。
- 只写"做了什么"，理由放 body。

### body（可选，默认省略）

- 仅在以下情况写：改动原因不直观、方案有明显取舍、影响面需要提醒。
- 写"为什么这么做"和"放弃了什么方案"，**不复述 diff**。
- 与 subject 之间空一行，每行 ≤ 72 字符。

### footer（按需）

- 破坏性变更：`BREAKING CHANGE: 说明影响了什么、如何迁移`。
- 关联任务：`Closes #123` / `Refs #456`。

## 原子性红线（违反 = 打回）

1. **一个 commit 只做一件事**。发现 diff 里混了多个不相关改动（如修 bug 顺手重构了别的模块），先给出拆分方案（每条该包含哪些文件/区块），再分别生成 message。
2. **message 与改动必须一致**。message 写 fix，diff 里却夹带新功能或无关格式化——指出问题，不帮着掩盖。
3. **敏感文件拦截**：发现 `.env`、密钥、credentials、含个人绝对路径的配置被提交，立即警告并建议移出提交。
4. **main/master 分支不写 `wip`**。临时提交只能在个人分支存在，合并前必须 squash 或改写。

## 信息量要求（反废话）

**判断标准：三个月后只看 message，不看 diff，能否知道改了什么、为什么。**

### 禁用写法（零信息量，直接打回）

- `update`、`修改`、`fix bug`、`优化`、`调整`、`完善`、`提交代码`
- `优化代码结构，提升可读性`、`修复已知问题` 这类放之四海皆准的空话
- 罗列文件名（`modified a.py, b.py`——diff 里本来就有）

### 常见 AI 痕迹（必须删除）

- 过度礼貌的解释腔："本次提交对用户模块进行了如下调整……"
- 每条 commit 都配一大段 body，把 diff 复述一遍
- 排比式总结："提升了稳定性、增强了体验、优化了性能"
- 滥用 emoji——除非仓库历史明确使用 gitmoji，否则一个不加

## 改写示例

**改前**：`fix bug`
**改后**：`fix(order): 修复优惠券叠加使用时金额计算错误`

**改前**：`update user module`
**改后**：`refactor(user): 抽离手机号校验逻辑为独立函数`

**改前**：`优化了一下登录` 
**改后**：`perf(auth): 登录接口去掉重复的权限查询，RT 从 800ms 降至 300ms`

**含破坏性变更**：

```text
refactor(api)!: 统一错误码格式为 { code, message }

旧版直接返回字符串错误信息，前端需同步调整解析逻辑。

BREAKING CHANGE: /api/v1 所有接口的错误响应体结构变更
Closes #88
```

## 批量整理提交记录时

执行 rebase/squash 整理任务时，输出格式为：

1. 先列出建议的提交划分（哪几个 commit 合并、哪几个拆分）；
2. 每条给出新 message；
3. 末尾附对应的 git 操作建议（如 `git rebase -i HEAD~5` 中各条的 pick/squash/reword 安排）。

## 交付前自检清单

- [ ] 已看过仓库历史，格式与语言跟随仓库主流风格？
- [ ] type 在白名单内且归类符合主要意图？scope 是真实模块名而非生造词？
- [ ] subject ≤ 50 字符（中文 ≤ 25 字）、动词开头、无结尾标点、无"了"？
- [ ] message 与 diff 内容完全一致，无夹带、无夸大？
- [ ] 无零信息量写法（update/优化/调整/fix bug）？
- [ ] 多个不相关改动已拆分？
- [ ] 无敏感文件混入提交？
- [ ] breaking change / issue 关联已写入 footer？
- [ ] 三个月后只看 message 能看懂改了什么？
